## 新技术的诱惑

每隔几个月，前端社区就会出现一个新的框架。每一个都承诺解决前一个的所有问题。每一个都有令人兴奋的 demo 和热情的早期采用者。

作为工程师，我们天然地被新技术吸引。学习新东西是我们的本能，也是我们保持竞争力的方式。但在个人项目中——尤其是那些你希望能运行 5 年、10 年的项目中——这种本能可能是有害的。

## 「无聊」的定义

当我说「无聊的技术」时，我指的是：

1. **已经存在至少 5 年**：经过了时间的检验
2. **有大量的生产环境使用案例**：不是实验性的
3. **文档完善，社区成熟**：遇到问题能找到答案
4. **核心团队稳定**：不会突然被放弃
5. **向后兼容性好**：升级不会破坏现有代码

具体来说：

| 无聊的选择 | 有趣的选择 |
|---|---|
| HTML + CSS + 少量 JS | 最新的全栈框架 |
| SQLite | 新出的分布式数据库 |
| Nginx | 最新的边缘计算平台 |
| Markdown | 自定义的富文本格式 |
| Git | 新的版本控制系统 |
| Cron | 新的任务调度框架 |

## 为什么无聊更好

### 1. 认知负担最小化

无聊的技术你已经会了。你不需要花时间学习新的概念模型、新的 API、新的最佳实践。你可以把所有认知资源用在**解决实际问题**上，而不是**学习工具**上。

```
# 使用无聊技术的时间分配
实际功能开发: 80%
工具学习和调试: 10%
维护和升级: 10%

# 使用新技术的时间分配
实际功能开发: 40%
工具学习和调试: 40%
维护和升级: 20%
```

### 2. 故障模式已知

无聊的技术的 bug 已经被发现并修复了。它的边界情况已经被文档化了。它的性能特征已经被测量了。

当你在凌晨 2 点遇到一个问题时，Stack Overflow 上大概率已经有人问过并得到了解答。

### 3. 长期可维护

想象一下 5 年后的你，需要修改这个项目的一个小功能。如果你用的是 2026 年最热门的框架，5 年后它可能：

- 已经被社区放弃
- 经历了多次不兼容的大版本升级
- 文档链接已经失效
- 核心维护者已经转向了新项目

但如果你用的是 HTML、CSS、和一个成熟的静态站点生成器，5 年后它大概率还是能正常工作的。

### 4. 依赖最少

无聊的技术通常意味着更少的依赖。更少的依赖意味着：

- 更少的安全漏洞风险
- 更少的版本冲突
- 更快的构建速度
- 更小的部署体积

```json
// 无聊项目的 package.json
{
  "dependencies": {
    "astro": "^5.0.0"
  }
}

// 有趣项目的 package.json
{
  "dependencies": {
    "next": "^15.0.0",
    "react": "^19.0.0",
    "react-dom": "^19.0.0",
    "@tanstack/react-query": "^6.0.0",
    "zustand": "^5.0.0",
    "tailwindcss": "^4.0.0",
    "framer-motion": "^12.0.0",
    "prisma": "^6.0.0",
    "@auth/core": "^2.0.0",
    "zod": "^4.0.0",
    // ... 还有 30 个
  }
}
```

每一个依赖都是一个潜在的故障点。每一个依赖都需要定期更新。每一个依赖都可能在某天发布一个不兼容的版本。

## 本项目的技术选型

Quiet Archive 的技术选型就是这个哲学的实践：

- **Astro**：成熟的静态站点生成器，输出纯 HTML
- **Markdown**：40 年历史的文本格式，永远可读
- **Python 脚本**：构建时的数据处理，不引入运行时依赖
- **Nginx**：20+ 年历史的 Web 服务器，稳如磐石
- **Git**：版本控制的事实标准
- **JSON**：数据交换的通用格式

没有数据库服务器、没有容器编排、没有微服务、没有消息队列。不是因为这些技术不好，而是因为**这个项目不需要它们**。

## 什么时候选择「有趣」

无聊技术栈不是教条。以下情况可以考虑新技术：

1. **学习项目**：专门用来学习新技术的项目，不需要长期维护
2. **核心需求匹配**：新技术恰好解决了你的核心问题，而旧技术做不到
3. **团队已有经验**：团队中有人深入使用过这个技术，不是从零开始
4. **有退出策略**：如果新技术失败了，你知道如何回退

关键问题：**你是在为项目选择最合适的技术，还是在为自己选择最有趣的技术？**

## 一个实用的决策框架

当你面临技术选型时，问自己：

```
1. 这个技术 3 年后还会存在吗？
   - 是 → 继续评估
   - 不确定 → 谨慎

2. 我能在 30 分钟内解释清楚它的工作原理吗？
   - 是 → 继续评估
   - 否 → 可能过于复杂

3. 如果这个技术明天消失，我能在一周内迁移到替代方案吗？
   - 是 → 风险可控
   - 否 → 高风险依赖

4. 去掉这个技术，项目还能工作吗？
   - 是 → 它是可选的增强，可以大胆尝试
   - 否 → 它是核心依赖，必须选择无聊的选项
```

## 结语

选择无聊的技术不是因为害怕新事物，而是因为**尊重时间**。

你的个人项目是你思想的载体。它应该在你不关注它的时候依然安静地运行，在你 5 年后回来时依然能被理解和修改。

无聊的技术给你这个保证。有趣的技术不能。

> Choose boring technology. Save your innovation tokens for the problems that actually need them.
> — Dan McKinley
